# SQL Query Analysis & Optimization: Anti-pattern Detection, LLM Rewriting, Equivalence Checking, Index Advisors (state as of Oct 2026)

Context for the reader: sqltext currently has (a) ~10 sqlglot static rules, (b) EXPLAIN readers for PG (JSON), MySQL/MariaDB (tabular), SQLite (EXPLAIN QUERY PLAN), none for SQL Server, (c) single-column CREATE INDEX suggestions, (d) an LLM rewrite that is accepted if it returns the same rows on current data (≤5000 rows) and has lower planner cost. The notes below are organized by key question; each ends with inferences/recommendations specific to sqltext.

## Q1. Static anti-pattern linters and rule catalogs we could reuse or port

### Takeaway
No single open-source "performance linter" exists. The best reusable catalogs are SQLFluff's AM/ST/CV/RF rules (MIT, Python, importable as a library), sqlcheck's anti-pattern catalog (Apache-2.0, C++, only worth porting rule ideas), squawk's Postgres-migration safety rules (relevant for the CREATE INDEX statements sqltext emits), and sqlglot's own optimizer passes (MIT), which can also be used as a canonicalizer. Commercial tools (pgMustard, pganalyze, EverSQL/Aiven) publish their categories but not their rule logic.

### Cited Findings
- **SQLFluff** 4.4.0 (current PyPI release, MIT license) ships rule groups including: AM01 "Ambiguous use of DISTINCT in a SELECT with GROUP BY", AM02 "UNION [DISTINCT|ALL] is preferred over just UNION", AM04 "Query produces an unknown number of result columns" (SELECT *), AM05 join clauses should be fully qualified, AM07 set-query column-count mismatch, AM08 "Implicit cross join detected", AM09 "LIMIT/OFFSET without ORDER BY may lead to non-deterministic results", CV05 "Comparisons with NULL should use IS / IS NOT", CV12 "Use JOIN ... ON instead of WHERE for join conditions", RF01 references to objects not in FROM, ST03 unused CTE, ST05 subqueries in FROM/JOIN, ST10 redundant constant expression, ST11 "Joined table not referenced in query". (Rule list obtained by installing sqlfluff 4.4.0 and enumerating `Linter().get_rulepack().rules` in a scratch venv this session.) — [sqlfluff on PyPI](https://pypi.org/project/sqlfluff/); [SQLFluff rules reference](https://docs.sqlfluff.com/en/stable/reference/rules.html)
- **sqlcheck** (Apache-2.0, C++) catalog: Logical design (Multi-Valued Attribute, Recursive Dependency, Primary Key Does Not Exist, Generic Primary Key, Foreign Key Does Not Exist, Entity-Attribute-Value, Metadata Tribbles); Physical design (Imprecise Data Type, Values In Definition, Files Are Not SQL Data Types, Too Many Indexes, Index Attribute Order); Query (SELECT *, NULL Usage, NOT NULL Usage, String Concatenation, GROUP BY Usage, ORDER BY RAND Usage, Pattern Matching Usage, Spaghetti Query Alert, Reduce Number of JOINs, Eliminate Unnecessary DISTINCT Conditions, Implicit Column Usage, HAVING Clause Usage, Nested Subqueries, OR Usage, UNION Usage, DISTINCT & JOIN Usage); Application (Readable Passwords); three risk levels. Latest version 1.3. — [jarulraj/sqlcheck](https://github.com/jarulraj/sqlcheck)
- **squawk** is a Postgres *migration* linter: "Squawk's rules focus on ensuring safe migrations and warn about statements that could block reads / writes or break existing clients." 60+ rules including `require-concurrent-index-creation`, `ban-concurrent-index-creation-in-transaction`, `require-concurrent-index-deletion`, `require-statement-timeout`, `require-lock-timeout`, `adding-foreign-key-constraint`, `constraint-missing-not-valid`, `changing-column-type`, `prefer-bigint-over-int`, `prefer-timestamptz`, `prefer-robust-stmts`. — [squawk rules](https://squawkhq.com/docs/rules)
- **sqlglot optimizer** (sqlglot 30.21.0, MIT) runs these passes in order: `qualify, pushdown_projections, normalize, unnest_subqueries, pushdown_predicates, optimize_joins, eliminate_subqueries, merge_subqueries, eliminate_joins, eliminate_ctes, quote_identifiers, annotate_types, canonicalize, simplify` (enumerated from `sqlglot.optimizer.optimizer.RULES` this session). sqlglot also has a pure-Python executor (`sqlglot.executor.execute(sql, schema, tables=...)`) that can run queries over in-memory tables. — [sqlglot on PyPI](https://pypi.org/project/sqlglot/); [sqlglot GitHub](https://github.com/tobymao/sqlglot)
- **pgMustard** (commercial) scores plan "tips" 0–5 by "estimated time-saving potential"; categories include Row Estimate (poor row estimates), Index Potential, Read Efficiency ("can be a sign of bloat"); it has a scoring API returning score, title, explanation, links, category. — [pgMustard scoring API](https://www.pgmustard.com/docs/scoring-api); [pgMustard read-efficiency post](https://www.pgmustard.com/blog/read-efficiency-issues-in-postgres-queries); [pgMustard changelog](https://www.pgmustard.com/changelog)
- **pganalyze** (commercial) Indexing Engine: extracts candidates from scans in the workload, considers "single-column, multi-column, and partial indexes" (B-tree and GiST), uses "what-if analysis" with "costing logic aligning with the Postgres cost model", and a deterministic "constraint programming model" for final selection (no ML). — [pganalyze Indexing Engine docs](https://pganalyze.com/docs/indexing-engine)
- **EverSQL** was acquired by Aiven (Nov 2023) and folded into Aiven's PostgreSQL/MySQL offering (Aiven AI Database Optimizer) — it is no longer an independent tool to integrate. — [Aiven press release](https://aiven.io/press/aiven-acquires-eversql)

### Inferences
- Rules sqltext lacks that are cheap to add on sqlglot ASTs (ideas from SQLFluff/sqlcheck): `= NULL`/`<> NULL` comparisons (CV05, a correctness bug, not just perf); LIMIT/OFFSET without ORDER BY (AM09, non-determinism; it also breaks the "same rows" check); implicit cross join via comma-FROM without predicate (AM08 overlaps the existing Cartesian rule); joined-but-unreferenced table (ST11, a classic "eliminate join" opportunity); `ORDER BY RAND()`; OFFSET-based deep pagination; functions on indexed columns in JOIN conditions (extension of non-sargable); implicit type coercion in predicates (column of type text compared to number; needs schema); `COUNT(*) > 0` vs `EXISTS`; `IN (SELECT ...)` with nullable column (extension of NOT IN rule); HAVING filters that could be WHERE (sqlcheck "HAVING Clause Usage"); redundant DISTINCT over a PK/unique key (sqlcheck "Eliminate Unnecessary DISTINCT"; needs schema); "Too Many Indexes" / "Index Attribute Order" (schema-level).
- Rather than port, sqltext can call SQLFluff as a library (MIT, pure Python) for the AM/ST/CV subset and map its findings into sqltext's finding model; sqlcheck is C++ and its last release (1.3) is old, so port ideas, don't depend on it.
- Because sqltext emits CREATE INDEX statements, it should follow squawk's guidance: emit `CREATE INDEX CONCURRENTLY` for Postgres (and warn it cannot run inside a transaction), and suggest `SET lock_timeout`/`statement_timeout` around DDL. Optionally run squawk (CLI) on generated DDL.
- sqlglot's optimizer passes (`unnest_subqueries`, `eliminate_joins`, `merge_subqueries`, `simplify`) are a deterministic, rule-based rewriter sqltext already has as a dependency. A cheap "rule-based rewrite" candidate (sqlglot-optimized SQL) can be proposed alongside the LLM rewrite, and comparing canonicalized forms of original vs rewrite gives a fast syntactic-equivalence check (but sqlglot's passes are not formally verified, so treat a match as strong evidence, not proof).

### Gaps
- squawk's license was not confirmed on the page fetched (I believe it is GPL-3.0 but did not verify; check before bundling). pgMustard's full tip list (e.g., whether "operation spills"/"lossy bitmaps" are separate categories) was not found in public docs.
- sqlcheck maintenance status: the fetched README claimed "active development", but I could not verify recent commit dates (GitHub API was blocked in this session); treat it as low-activity.
- sqlglot's own optimizer docs page URL returned 404; rule list was taken from the installed package instead.

## Q2. LLM-based query rewriting research: systems, reported speedups, and how they verify correctness

### Takeaway
Two families exist: (1) LLM-guided *rule selection* over Apache Calcite rules (LearnedRewrite, LLM-R2, R-Bot), which preserve equivalence by construction but are limited by Calcite's parser and rule set; (2) *free-form* LLM rewriting (GenRewrite, LITHE, QUITE, E3-Rewrite), which finds more speedups but produces many wrong rewrites (~32% gave different results in Microsoft's real-world study), so every system wraps it in a multi-stage verification cascade: formal checker (SQLSolver/QED) → bounded/counterexample tester or LLM judge → result comparison on sampled/full data. None of them trust result equality on one dataset alone, and the best ones measure real runtime rather than trusting planner cost.

### Cited Findings
- **Microsoft study (CIDR 2026, Narasayya & Chaudhuri)**: on SQL Server with 118 real-world queries over 4 enterprise DBs plus 224 JOB/TPC-DS/TPC-H queries, "a large fraction of the rewrites (≈32%) produce different results compared to the original query on the given database, and are therefore incorrect." Matching results "over the given database (or a set of test databases) is only a necessary condition but not sufficient for equivalence." Median-query improvement of the best verified rewrite was ≤6%, but at P90 improvements were 79%/83%/63% (all/benchmark/real). — [Leveraging Query Optimizers to Verify the Soundness of LLM-based Query Rewrites (CIDR 2026)](https://www.vldb.org/cidrdb/papers/2026/p33-narasayya.pdf)
- Same paper: "on TPC-DS the state-of-the-art query equivalence checkers are unable to verify equivalence for any of the LLM generated rewrites"; they "experimented with QED and found that it is unable to verify any of the LLM-generated rewrites" for the real-world queries. Their alternative, **QO-Verify**, exports the optimizer's memo for both queries (cost-based pruning and timeouts off) and returns True if any logical expression is shared, else Unknown; no false positives; verified ≈37% (1150+ of 3100+) of candidate rewrites, 31–48% per database, median runtime ~1.2 s. It requires engine internals (implemented inside SQL Server), so it is not available to external tools. — [CIDR 2026 paper](https://www.vldb.org/cidrdb/papers/2026/p33-narasayya.pdf)
- **LITHE (EDBT 2026)**: GPT-4o, prompts augmented with database-aware rules, plus token-probability-guided MCTS. On TPC-DS/PostgreSQL v16 it found "highly productive" (>1.5× estimated cost speedup) rewrites for 26 queries vs ~13 for SOTA; cost-speedup geometric mean 11.5 vs 6.1; runtime-speedup GM for slow queries 13.2 vs 4.9. Verification: (1) result equivalence on several small samples using correlated sampling, constant adjustment so predicates select rows, and injected synthetic tuples "similar to the XData mutant-killing tool" for boundary conditions; (2) logic-based QED and SQLSolver ("these two approaches covered a larger set of queries"); (3) full-database result comparison if inconclusive. Of 27 productive rewrites, only 11 could be formally verified; 16 passed statistical tests only. It also has "regression identification": parameterize constants and check plan "replacement safety" at the corners of the selectivity space (SEER), because "there are often material discrepancies between optimizer cost predictions and actual execution times." — [LITHE paper (EDBT 2026)](https://openproceedings.org/2026/conf/edbt/paper-93.pdf)
- **GenRewrite (Liu & Mozafari, arXiv v3 Dec 2025)**: free-form LLM rewriting with "Natural Language Rewrite Rules" and counterexample-guided correction. At ≥2× on TPC-DS it improves 25 queries (1.35× more than LLM baselines, 2.6× more than LLM-enhanced rule-based baselines). Correctness gate: SQLSolver first; if UNKNOWN, fall back to the SlabCity tester (hint-guided input generation); "If neither the verifier nor the tester can certify equivalence, we abstain." SQLSolver "can verify only 18.9% of the generated TPC-DS rewrites" (74.4% on JOB). It notes all Calcite-based systems (LLM-R2, R-Bot, LearnedRewrite) inherit Calcite parser and rule coverage limits. Performance gate: offline shadow execution. — [GenRewrite (arXiv 2403.09060)](https://arxiv.org/abs/2403.09060)
- **QUITE (arXiv 2506.07675, v3 Jan 2026)**: training-free multi-agent (FSM-controlled) LLM rewriter with a "rewrite middleware" and *hint injection* (pg_hint_plan-style `/*+ HashJoin(...) */`, `NoNestLoop`, `Rows(a b #10)` etc.); up to 35.8% execution-time reduction over SOTA (21.9% in the intro vs best alternative) and 24.1% more rewrites. Verification: SQLSolver first; if unknown, iterative LLM-based verification/correction. — [QUITE (arXiv 2506.07675)](https://arxiv.org/abs/2506.07675)
- **E3-Rewrite (arXiv 2508.09023)**: RL-trained LLM rewriter with rewards for executability, equivalence and efficiency; up to 25.6% lower execution time than baselines and up to 24.4% more equivalent rewrites; on TPC-H average latency 78.81 s → 29.67 s. Equivalence reward: QED-Solver; if unknown, LLM judgment; if inconclusive, compare results on sampled DB instances. Efficiency reward uses optimizer-estimated EXPLAIN cost. — [E3-Rewrite (arXiv 2508.09023)](https://arxiv.org/abs/2508.09023)
- **R-Bot (PVLDB 2025, Tsinghua/Huawei)**: LLM selects and orders Calcite rewrite rules using RAG over rule specs and Q&A "evidence", so equivalence follows from the rules; on TPC-H 50× and DSB 50×, overall latency improvements of 1.82× and 1.68×; on a bank's real workload, improved 70% of 20 slow queries, overall 9.23 h → 4.37 h; deployed at Huawei. Code: github.com/curtis-sun/LLM4Rewrite. — [R-Bot (arXiv 2412.01661)](https://arxiv.org/abs/2412.01661)
- **LLM-R2 (PVLDB, Alibaba DAMO/NTU)**: LLM proposes Calcite rewrite rules, with a contrastively trained demonstration selector; reduces execution time to 52.5%, 56.0%, 39.8% of the original on TPC-H, IMDB and DSB. Code: github.com/DAMO-NLP-SG/LLM-R2. — [LLM-R2 (arXiv 2404.12872)](https://arxiv.org/abs/2404.12872)
- **WeTune (SIGMOD 2022, SJTU)**: superoptimization-style enumeration of query-plan templates plus an SMT verifier under enumerated constraints; discovered rules optimize 247 queries from 20 popular open-source web apps that existing DBs could not optimize. — [WeTune paper](https://ipads.se.sjtu.edu.cn/_media/publications/wetune_final.pdf)
- **QueryBooster (PVLDB 16(11), 2023)**: middleware for human-centered rewriting with the VarSQL rule language (Pattern / Replacement / Constraints / Actions, with variables for tables, columns, predicates, subqueries); can generalize rules from user-provided before/after examples. — [QueryBooster (arXiv 2305.08272)](https://arxiv.org/abs/2305.08272)

### Inferences
- sqltext's current gate ("same rows on ≤5000 rows of current data" + "lower planner cost") is the weakest stage of the cascade every paper uses. With ~32% of LLM rewrites wrong on real data, and many wrong ones still matching on small or unrepresentative data, sqltext should (a) report a verification *level* instead of a binary accept, and (b) add stronger stages (formal checker → targeted counterexample DBs → full or sampled data), abstaining when nothing certifies (GenRewrite's policy).
- Prompting ideas worth copying: GenRewrite-style reusable natural-language rewrite hints learned from accepted rewrites; LITHE-style DB-aware rules in the prompt (redundancy removal, selectivity-based rewrites); counterexample feedback (re-prompt with the distinguishing DB/rows when a rewrite fails); limit retries (CIDR used ≤3 LLM calls with errors appended).
- Prefer "restricted-scope" prompts: the CIDR study found verification coverage varies a lot by prompt (hint prompts verified most often; subquery/CTE prompts ~1 in 5 / 1 in 4), so asking the LLM for specific transformations (decorrelate, NOT IN→NOT EXISTS, OR→UNION ALL) yields more verifiable rewrites than "optimize this".
- A rule-based track (sqlglot optimizer passes, or a small catalog of verified transformations in VarSQL-like pattern form) is equivalence-preserving by construction and complements the LLM track.

### Gaps
- LLM-QO and LearnedRewrite (Zhou et al., MCTS over Calcite rules) were not researched in detail this session; GenRewrite/R-Bot describe LearnedRewrite only as a Calcite-based baseline.
- No public code was confirmed for LITHE, QUITE, E3-Rewrite or GenRewrite (only R-Bot and LLM-R2 list GitHub repos in their papers).
- Speedup figures come from the authors' own benchmarks (mostly TPC-H/TPC-DS/DSB/JOB on PostgreSQL), which the CIDR paper notes may be in LLM training data; real-world gains were much smaller at the median.

## Q3. Query equivalence checkers and counterexample-based testing: usable implementations, SQL subsets, runtime, Python callability

### Takeaway
Three checkers are practical to call from Python as subprocesses: **SQLSolver** (Java 17 jar, Apache-2.0, Calcite SQL syntax, EQ/NEQ/UNKNOWN/TIMEOUT), **QED** (Rust, cvc5+z3, bag semantics, no ORDER BY/LIMIT, weak aggregates), and **VeriEQL** (Python + Z3, *bounded* equivalence with counterexample DBs, supports ORDER BY, CASE, outer joins, integrity constraints). Formal proofs succeed on only a minority of realistic LLM rewrites (SQLSolver 18.9% of TPC-DS rewrites; 0% on TPC-DS per Microsoft), so they must be combined with counterexample generation (VeriEQL, Polygon, XData-style mutation) and data-based testing.

### Cited Findings
- **SQLSolver** (SIGMOD 2024, "Proving Query Equivalence Using Linear Integer Arithmetic", SJTU-IPADS): Java 17, Apache-2.0; needs Z3 4.8.9, ANTLR 4.8, Gradle; CLI `java -jar sqlsolver.jar -sql1=<path> -sql2=<path> -schema=<path>` where schema is CREATE TABLE statements and each SQL file holds one statement per line (paired by line); "Compatible with Apache Calcite parser syntax"; returns UNKNOWN (unsupported features/syntax errors), NEQ (may be false negatives), or TIMEOUT; Java API `Verification.verify()` with timeout. Research-grade (16 commits). — [SJTU-IPADS/SQLSolver](https://github.com/SJTU-IPADS/SQLSolver)
- **QED** (PVLDB 17, 2024; Wang, Pan, Cheung): Q-expressions with normal forms under bag semantics, models integrity constraints and NULLs; proves 299/444 Calcite rule pairs and 979/1287 CockroachDB pairs, >2× prior SOTA; ~0.35–0.88 s average per pair. Implemented in 2,520 lines of Rust with cvc5 and z3 run in parallel; 60 s default timeout. Limitations: "does not support queries that make use of the ordering semantics of Limit, Offset, or Order By", limited aggregate support, some operators uninterpreted. Code: github.com/qed-solver/prover. — [QED paper (PVLDB 17)](https://www.vldb.org/pvldb/vol17/p3602-wang.pdf)
- **VeriEQL** (OOPSLA 2024; He, Zhao, Wang, Wang): first SMT-based tool to prove *and disprove* bounded equivalence of complex SQL with integrity constraints; supports ORDER BY (bubble-sort encoding), CASE WHEN, outer joins, group-by/aggregates, subqueries; on 24,455 benchmarks it solves 77% vs <2% for prior bounded verifiers and <1% for testing tools; generates counterexamples that found bugs in MySQL and Calcite; bound increases from 1 until timeout (10-min limit in experiments). — [VeriEQL (arXiv 2403.03193)](https://arxiv.org/abs/2403.03193)
- VeriEQL repo: Python 3.10+ (3.11 recommended), input as JSON-lines of query pairs, CLIs `python -m parallel.cli_within_timeout -f X.jsonlines -t 600` and `python -m parallel.cli_within_bound -f X.jsonlines -s 10`; license file `license.md` (type not shown); experiments dated to at least Oct 2025. — [VeriEQL/VeriEQL on GitHub](https://github.com/VeriEQL/VeriEQL)
- VeriEQL paper notes UDP has no usable public artifact and that the SPES artifact accepts fewer constraints than the paper claims; it also reports Cosette "may have an implementation bug that led to spurious counterexamples." — [VeriEQL (arXiv 2403.03193)](https://arxiv.org/pdf/2403.03193)
- **Polygon** (PLDI 2025; same group as VeriEQL): symbolic reasoning engine that generates inputs for n queries so their outputs satisfy a property, used for "SQL equivalence refutation and query disambiguation"; uses conflict-driven search over under-approximations; evaluated on >30,000 benchmarks, "significantly outperforms all prior techniques." — [Polygon (arXiv 2504.06542)](https://arxiv.org/abs/2504.06542); [PLDI 2025 listing](https://pldi25.sigplan.org/details/pldi-2025-papers/54/Polygon-Symbolic-Reasoning-for-SQL-using-Conflict-Driven-Under-Approximation-Search)
- Coverage in practice: GenRewrite reports SQLSolver verifies 18.9% of generated TPC-DS rewrites and 74.4% on JOB — [GenRewrite](https://arxiv.org/abs/2403.09060); LITHE formally verified 11 of 27 productive TPC-DS rewrites with QED+SQLSolver — [LITHE](https://openproceedings.org/2026/conf/edbt/paper-93.pdf); Microsoft says SMT-based checkers "particularly fall short for queries with aggregation" and fail on all LLM TPC-DS rewrites — [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p33-narasayya.pdf).
- Counterexample/testing approaches used in practice: LITHE's correlated sampling + constant adjustment + injected boundary tuples "similar to the XData mutant-killing tool" — [LITHE](https://openproceedings.org/2026/conf/edbt/paper-93.pdf); GenRewrite's SlabCity tester (hint-guided input generation), with counterexamples fed back into the tester — [GenRewrite](https://arxiv.org/abs/2403.09060).
- LLMs as equivalence judges are studied ("Can the Rookies Cut the Tough Cookie? Exploring the Use of LLMs for SQL Equivalence Checking"); QUITE and E3-Rewrite use an LLM judge only as a fallback after a formal tool returns unknown. — [arXiv 2412.05561](https://arxiv.org/pdf/2412.05561); [QUITE](https://arxiv.org/abs/2506.07675); [E3-Rewrite](https://arxiv.org/abs/2508.09023)

### Inferences
- Recommended verification cascade for sqltext (cheapest first, each producing a labeled verdict):
  1. **Syntactic/canonical**: sqlglot `optimize()` + canonical SQL comparison of both queries (with schema) → "canonically identical" (strong but heuristic).
  2. **Formal proof** (optional plugin, subprocess with timeout ~10–60 s): SQLSolver jar (needs JRE; translate dialect SQL to Calcite-compatible ANSI with sqlglot first) and/or QED (Rust binary; skip if ORDER BY/LIMIT present). EQ → "PROVEN"; NEQ → reject.
  3. **Bounded check + counterexamples**: VeriEQL (Python, easiest to integrate; check its license first) with small bound (2–5 rows/table) → "bounded-equivalent up to N" or a concrete counterexample DB to show the user and feed back to the LLM.
  4. **Differential testing on synthesized DBs**: generate small edge-case databases (NULLs in every nullable column, duplicate rows, empty tables, values exactly at predicate constants ±1, strings matching/not matching LIKE patterns, FK-orphan rows) in a temp SQLite/scratch schema and compare multisets; plus current data. Note SQL semantics differ across engines, so run tests on the target engine (temp schema / transaction) when possible.
  5. **Current-data comparison** (what sqltext does today) as a necessary-but-not-sufficient check; compare as multisets (bag semantics), compare ordered only if top-level ORDER BY is total; treat `LIMIT` without total ORDER BY as non-deterministic.
  Accept automatically only on PROVEN; otherwise present "TESTED (n DBs, m rows)" with explicit caveats, mirroring LITHE's "provable vs statistical" label.
- The 5000-row cap on current data both weakens the equivalence evidence and makes cost comparisons unrepresentative (see Q5/Q6).

### Gaps
- Cosette (Rosette/Lean based), SPES, EQUITAS: no current maintenance/license status was verified this session; the VeriEQL paper's remarks suggest Cosette and SPES artifacts are dated. EQUITAS was not researched.
- QED's repo license and maintenance were not verified (GitHub API blocked). VeriEQL's license type was not visible.
- Polygon code availability not confirmed. XData's current availability (IIT Bombay) not checked.
- No source found giving SQLSolver/QED coverage on MySQL- or T-SQL-specific syntax; assume dialect translation via sqlglot is needed.

## Q4. Index advisors and estimating an index's benefit without creating it

### Takeaway
Postgres has a mature what-if stack: **HypoPG** (session-local hypothetical indexes visible to plain EXPLAIN), with **Dexter** (MIT, CLI) and **Supabase index_advisor** (PostgreSQL license, SQL function returning before/after costs and DDL) built on it, and **pg_qualstats** for workload predicate stats. SQL Server's optimizer emits **MissingIndexes** (with estimated impact %) in SHOWPLAN XML without executing the query. SQLite has an experimental **`.expert`** (sqlite3_expert) recommender. MySQL/MariaDB have no built-in hypothetical index; invisible (MySQL) / ignored (MariaDB) indexes only help test *removing* or *toggling* real indexes. LLM-based index advisors (LLMIA, LLMIdxAdvis) exist in research but still rely on what-if cost calls.

### Cited Findings
- **HypoPG**: supports btree, brin, hash (PG10+), bloom; `hypopg_create_index('CREATE INDEX ...')`, `hypopg_relation_size(oid)` (estimated index size), `hypopg_hide_index`/`unhide` (simulate dropping a real index), `hypopg_reset()`. Indexes live "in connection private memory", not affecting other sessions; "HypoPG makes sure they will only be used using a simple EXPLAIN statement (without the ANALYZE option)." ~2,500 hypothetical indexes limit without `hypopg.use_real_oids`. — [HypoPG usage docs](https://hypopg.readthedocs.io/en/rel1_stable/usage.html)
- **Dexter** (ankane/dexter, MIT): reads queries from pg_stat_statements, pg_stat_activity, log files or SQL files; uses HypoPG + pg_query; options `--create`, `--analyze`, `--min-calls`, `--min-time`, `--exclude/--include`; recommends indexes when hypothetical-index cost savings exceed a threshold. Latest 0.6.3 (2025-10-15), 0.6.0 (2025-06-01) dropped PostgreSQL <13. HypoPG is unavailable on some managed providers (e.g., Google Cloud SQL, DigitalOcean per README). — [ankane/dexter](https://github.com/ankane/dexter); [Dexter CHANGELOG](https://github.com/ankane/dexter/blob/master/CHANGELOG.md); [Percona on pg_qualstats+hypopg](https://www.percona.com/blog/automatic-index-recommendations-in-postgresql-using-pg_qualstats-and-hypopg/)
- **Supabase index_advisor** (PostgreSQL license, v0.2.0, ~1.7k stars): `index_advisor(query text) returns (startup_cost_before, startup_cost_after, total_cost_before, total_cost_after jsonb, index_statements text[], errors text[])`; requires PG13+ and HypoPG; accepts parameterized queries (`$1`); handles joins across multiple tables, materialized views, and columns behind views. — [supabase/index_advisor](https://github.com/supabase/index_advisor)
- **pg_qualstats** tracks which columns appear in WHERE/JOIN predicates across the real workload (with selectivity), and is combined with hypopg for automatic recommendations. — [Percona blog](https://www.percona.com/blog/automatic-index-recommendations-in-postgresql-using-pg_qualstats-and-hypopg/)
- **SQL Server**: `SET SHOWPLAN_XML ON` makes SQL Server "not execute Transact-SQL statements" and return the plan as XML (nvarchar(max)) with estimated costs and rows; "It must be the only statement in a batch"; requires SHOWPLAN permission. — [SET SHOWPLAN_XML docs](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-showplan-xml-transact-sql). The plan XML contains `MissingIndexes` elements (equality/inequality/include columns and estimated cost reduction %, e.g. "34.2737%"); DMVs `sys.dm_db_missing_index_details/_groups/_group_stats/_columns` aggregate them. Limitations: estimates from a single optimization, not tested after execution; only nonclustered rowstore (no unique/filtered); no key-column order; no cost-benefit on INCLUDE size; none for trivial plans; less accurate for inequality-only predicates; max 600 groups; cleared on restart/metadata change. Guidance: equality columns before inequality columns, most selective first. — [Tune nonclustered indexes with missing index suggestions](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/tune-nonclustered-missing-index-suggestions)
- **MySQL invisible indexes**: `CREATE INDEX ... INVISIBLE` / `ALTER TABLE ... ALTER INDEX ... VISIBLE|INVISIBLE`; optimizer ignores them unless `optimizer_switch='use_invisible_indexes=on'` (settable per query via `/*+ SET_VAR(...) */`); "Index visibility does not affect index maintenance"; primary keys cannot be invisible. They test the effect of *removing* an index; the index still must be built. — [MySQL 8.4 invisible indexes](https://dev.mysql.com/doc/refman/8.4/en/invisible-indexes.html)
- **MariaDB**: IGNORED indexes (10.6+) are maintained but not used by the optimizer; optimizer trace (`optimizer_trace='enabled=on'`) produces JSON explaining chosen/rejected plans for SELECT/UPDATE/DELETE. — [MariaDB ignored indexes](https://mariadb.com/docs/server/ha-and-performance/optimization-and-tuning/optimization-and-indexes/ignored-indexes); [MariaDB optimizer trace](https://mariadb.com/kb/en/optimizer-trace-overview/)
- **SQLite `.expert`**: CLI command that "can assist with this by proposing indexes that might assist with specific queries, were they present in the database", outputs CREATE INDEX + EXPLAIN QUERY PLAN; based on `ext/expert` (sqlite3_expert); "experimental. It may be removed or the interface modified"; `--sample` option (default 0, schema-only). — [SQLite CLI docs](https://sqlite.org/cli.html)
- **pganalyze** what-if: candidate single/multi-column/partial indexes, Postgres-aligned cost model, constraint programming selection, explicit write-overhead modeling. — [pganalyze Indexing Engine](https://pganalyze.com/docs/indexing-engine)
- **LLM index advisors**: LLMIA (in-context learning, iterative DB feedback; evaluated on TPC-H, JOB, TPC-DS, SSB vs 12 baselines) — [LLMIA (arXiv 2503.07884)](https://arxiv.org/abs/2503.07884); also UTune (uncertainty-aware online index tuning, 2026) — [arXiv 2601.18199](https://arxiv.org/abs/2601.18199). Most methods still score candidates via what-if (hypothetical-index) EXPLAIN cost.

### Inferences
- Upgrade the index advisor from "single-column, any filtered column" to a **what-if-verified, composite** advisor:
  - Candidate generation (all engines, from sqlglot AST): per table, build composite candidates ordered equality-predicate columns → one range column → ORDER BY/GROUP BY columns, optional covering INCLUDE (PG11+/SQL Server); skip columns whose predicates are non-sargable; dedupe against existing indexes by leading-prefix match (an existing (a,b) covers (a)).
  - **PostgreSQL**: if `hypopg` is installed (`SELECT 1 FROM pg_extension WHERE extname='hypopg'`), create each candidate hypothetically, run plain `EXPLAIN (FORMAT JSON)`, keep candidates the planner actually uses and that cut total cost by a threshold (Dexter-style), report `hypopg_relation_size` as the size cost; call `index_advisor()` when installed. Without hypopg, fall back to heuristic suggestions labeled "unverified".
  - **SQL Server**: implement EXPLAIN via `SET SHOWPLAN_XML ON` as its own batch on the same pyodbc/pymssql connection, run the query (not executed), fetch the XML row, `SET SHOWPLAN_XML OFF`; parse `StatementSubTreeCost`, `EstimateRows`, operators, and `MissingIndexes` (impact %). This closes the "no EXPLAIN for SQL Server" gap and gives an engine-native index advisor.
  - **SQLite**: run `.expert` through the `sqlite3` CLI as a subprocess if available (or the sqlite3_expert C API via an extension), else heuristic; verify by building the index in a temporary copy/in-memory clone of the schema (cheap for SQLite) and checking EXPLAIN QUERY PLAN switches from `SCAN` to `SEARCH ... USING INDEX`.
  - **MySQL/MariaDB**: no hypothetical indexes found; options are (a) heuristic + `EXPLAIN FORMAT=JSON` cost on a scratch copy with the index actually built (only for small tables), or (b) label as unverified. Use invisible/ignored indexes to evaluate *dropping* redundant indexes.
- Always add write-cost and size caveats (pganalyze models write overhead; SQL Server docs warn every nonclustered index adds DML/maintenance overhead).

### Gaps
- I found no MySQL/MariaDB-native hypothetical index feature (no source confirms one exists or does not; this is based on absence in the docs consulted).
- "AI Meets AI" (Microsoft, SIGMOD 2019, classifier predicting whether an index will actually improve execution vs optimizer estimate) was not fetched this session; its core point (optimizer what-if estimates can be wrong, so regressions occur) is consistent with the SQL Server doc's "not tested after execution" caveat.
- LLMIdxAdvis numbers (reported by a search snippet: within ≤2 points of SOTA heuristics, 95% faster) were not verified against the paper.

## Q5. Using EXPLAIN ANALYZE / BUFFERS safely and reading plans for common problems

### Takeaway
EXPLAIN ANALYZE executes the statement in every engine (PostgreSQL, MySQL 8.0.18+ TREE output), so it must be wrapped: read-only/rolled-back transaction, statement-level timeout, and opt-in. Once actual rows/loops are available, sqltext can detect the most common problems mechanically: row misestimates (estimated vs actual×loops), nested loops with many loops, hash joins with Batches>1, external sorts, high "Rows Removed by Filter" ratios, and large buffer reads.

### Cited Findings
- PostgreSQL 18 docs: "Keep in mind that the statement is actually executed when the ANALYZE option is used." For INSERT/UPDATE/DELETE/MERGE/CREATE TABLE AS/EXECUTE wrap in `BEGIN; EXPLAIN ANALYZE ...; ROLLBACK;`. In PG18, "Buffers information is automatically included when ANALYZE is used." `GENERIC_PLAN` allows `$1` placeholders but "cannot be used together with ANALYZE". `SERIALIZE` (with ANALYZE) measures output conversion cost; `MEMORY` shows planner memory; `SETTINGS` lists non-default planner settings; `WAL` (with ANALYZE). — [PostgreSQL EXPLAIN (v18)](https://www.postgresql.org/docs/current/sql-explain.html)
- PostgreSQL "Using EXPLAIN": for repeated subplans "the loops value reports the total number of executions of the node, and the actual time and rows values shown are averages per-execution… Multiply by the loops value"; Hash node: "If the number of batches exceeds one, there will also be disk space usage involved"; Sort shows `Sort Method` (e.g., quicksort Memory: 74kB vs external merge on disk); "Rows Removed by Filter" lines; timing overhead "can be significant"; network/I/O conversion costs excluded unless SERIALIZE; "results on a toy-sized table cannot be assumed to apply to large tables… on a table that only occupies one disk page, you'll nearly always get a sequential scan plan whether indexes are available or not." — [Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)
- MySQL 8.4: `EXPLAIN ANALYZE` "runs a statement" and reports per iterator estimated cost, estimated rows, time to first row, time per iterator, actual rows, loops; always TREE format (FORMAT=JSON errors); works for SELECT, multi-table UPDATE/DELETE, TABLE; can be interrupted with KILL QUERY / Ctrl-C. — [MySQL EXPLAIN docs](https://dev.mysql.com/doc/refman/8.4/en/explain.html)
- MySQL provides a `MAX_EXECUTION_TIME(N)` optimizer hint to cap SELECT execution time. — [MySQL optimizer hints](https://docs.oracle.com/cd/E17952_01/mysql-8.0-en/optimizer-hints.html)
- SQL Server: `SET SHOWPLAN_XML ON` gives the estimated plan without executing; an actual plan requires executing (SET STATISTICS XML, per SSMS "actual execution plan"). — [SET SHOWPLAN_XML](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-showplan-xml-transact-sql)
- pgMustard treats poor row estimates and poor read efficiency (rows read vs returned, a sign of bloat or missing index) as headline tip categories. — [pgMustard scoring API](https://www.pgmustard.com/docs/scoring-api); [pgMustard read efficiency](https://www.pgmustard.com/blog/read-efficiency-issues-in-postgres-queries)

### Inferences
- Safe-execution recipe for an opt-in "--analyze" mode:
  - PostgreSQL: `BEGIN; SET LOCAL statement_timeout = '<N>s'; SET LOCAL lock_timeout = '1s'; SET TRANSACTION READ ONLY` (for SELECTs) → `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) ...` → `ROLLBACK`. Refuse ANALYZE on DML unless explicitly allowed (even rolled back, DML takes locks and fires triggers/side effects like sequences).
  - MySQL: `SELECT /*+ MAX_EXECUTION_TIME(ms) */` for SELECT, or session `max_execution_time`; EXPLAIN ANALYZE only on SELECT; parse TREE text.
  - SQL Server: default to SHOWPLAN_XML (no execution); actual plans only opt-in with `SET STATISTICS XML ON` plus a client-side query timeout.
  - SQLite: no ANALYZE equivalent; time the query with a progress-handler-based timeout (`conn.set_progress_handler`) in a read-only connection.
- Mechanical plan checks to add (PG JSON gives "Plan Rows", "Actual Rows", "Actual Loops", "Hash Batches", "Sort Method", "Sort Space Type", "Rows Removed by Filter", "Shared Read Blocks", "Temp Written Blocks"):
  - Misestimate: q-error = max(est, act)/min(est, act) using act = Actual Rows × Actual Loops vs Plan Rows × loops; flag ≥10× (warn) and ≥100× (severe) on nodes feeding joins; suggest ANALYZE/extended statistics (`CREATE STATISTICS` for correlated columns). (Thresholds are a design choice, not from a cited source.)
  - Nested Loop where inner side loops > ~1000 or outer actual rows ≫ estimated → likely misestimate-driven join choice.
  - Hash Batches > 1 or Sort Space Type = Disk or Temp Written Blocks > 0 → work_mem spill.
  - Seq Scan with Rows Removed by Filter / (rows + removed) > 0.9 on a large table → index candidate (feed into Q4 what-if).
  - Hidden cost of loops: always multiply per-loop time/rows by loops before ranking nodes.

### Gaps
- No primary source found this session for "standard" misestimation thresholds; the 10×/100× numbers above are an engineering suggestion.
- MariaDB's `ANALYZE FORMAT=JSON` (MariaDB's equivalent of EXPLAIN ANALYZE) was not re-verified in docs this session.

## Q6. Cost comparability caveats (planner cost units across queries and engines; SQLite has no cost)

### Takeaway
Planner cost is a unit-less, engine-specific estimate that is only loosely comparable even between two plans of the same engine, and it is derived from the same (possibly wrong) cardinality estimates that made the original query slow. Research systems treat cost as a filter (require a large margin like >1.5×) and then confirm with measured runtime or regression heuristics; sqltext should do the same and must use another signal for SQLite.

### Cited Findings
- PostgreSQL: "The costs are measured in arbitrary units determined by the planner's cost parameters… Traditional practice is to measure the costs in units of disk page fetches"; actual times are milliseconds while costs are arbitrary "so they are unlikely to match up." — [Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html)
- LITHE requires >1.5× optimizer-estimated speedup to count a rewrite as productive ("enough headroom in the optimizer prediction that a runtime regression is unlikely"), cites "material discrepancies between optimizer cost predictions and actual execution times", and adds a SEER-based regression test at selectivity-space corners. — [LITHE](https://openproceedings.org/2026/conf/edbt/paper-93.pdf)
- LLM-R2 motivates itself partly by "current query rewrite methods usually rely highly on DBMS cost estimators which are often not accurate." — [LLM-R2](https://arxiv.org/abs/2404.12872)
- QUITE injects hints because the optimizer may undo the LLM's intended plan "due to inaccurate cost estimations." — [QUITE](https://arxiv.org/abs/2506.07675)
- E3-Rewrite's efficiency reward uses EXPLAIN-estimated cost, while GenRewrite and the Microsoft study use measured execution (shadow execution; ≥2× runtime threshold, up to 3 LLM attempts). — [E3-Rewrite](https://arxiv.org/abs/2508.09023); [GenRewrite](https://arxiv.org/abs/2403.09060); [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p33-narasayya.pdf)
- SQL Server plan XML reports `EstimatedTotalSubtreeCost`/`StatementSubTreeCost`, and missing-index impact is a % reduction of that estimated cost, which is "less accurate for queries involving only inequality predicates." — [SET SHOWPLAN_XML](https://learn.microsoft.com/en-us/sql/t-sql/statements/set-showplan-xml-transact-sql); [Missing index suggestions](https://learn.microsoft.com/en-us/sql/relational-databases/indexes/tune-nonclustered-missing-index-suggestions)
- MySQL EXPLAIN ANALYZE/TREE prints per-iterator `cost=` estimates alongside actual time — [MySQL EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html). PostgreSQL warns toy-sized tables produce plans that do not extrapolate — [Using EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html).
- SQLite's `.expert` outputs only EXPLAIN QUERY PLAN text, no cost numbers. — [SQLite CLI](https://sqlite.org/cli.html)

### Inferences
- Replace "lower planner cost" with a decision rule: (1) only compare costs from the same engine, same connection/settings, same statistics; (2) require a margin (e.g., ≥1.5× like LITHE, or configurable) not merely "lower"; (3) when allowed, confirm with measured runtime: N warm runs each, median, under statement_timeout, alternating order (A,B,B,A) to reduce cache bias; (4) report "estimated" vs "measured" separately; (5) never compare costs across engines or across a dev DB with 5000 rows and production (plans on small data don't extrapolate; consider running EXPLAIN on prod-like stats or warn).
- For parameterized queries (PG16+ `EXPLAIN (GENERIC_PLAN)`), compare both generic-plan cost and a few representative constant values; LITHE's corner-selectivity idea suggests checking low/high selectivity constants to detect "brittle" rewrites.
- SQLite fallback: plan-shape scoring (count of `SCAN table` vs `SEARCH table USING INDEX`, `USE TEMP B-TREE FOR ORDER BY/DISTINCT`, correlated `CORRELATED SCALAR SUBQUERY`) plus measured wall time with timeout; label as "no cost model".
- Normalize the rewrite outcome report as: equivalence level (PROVEN / BOUNDED / TESTED / UNVERIFIED) × performance evidence (MEASURED x.x× / ESTIMATED x.x× / PLAN-SHAPE only). This is what makes the analyzer "trustworthy": users see exactly what was checked.

### Gaps
- No single source quantifies how often PostgreSQL/MySQL cost rank-order disagrees with runtime rank-order for rewrite pairs; LITHE notes "brittle" rewrites exist but the fetched text did not give a rate.
- I did not verify MySQL `EXPLAIN FORMAT=JSON` `query_cost` semantics across 8.0/8.4/9.x or MariaDB's cost model changes (MariaDB 11.0 reworked its cost model, per memory only; unverified this session).
